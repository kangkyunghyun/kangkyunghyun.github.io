## 서비스

습관을 지키지 못했을 때 실패로 끝내지 않고, 실패 기록을 분석해 다음 계획을 조정해 주는 AI 습관 관리 서비스입니다.

6인 팀(Design 1, Backend 2, Frontend 2, AI 1)에서 **팀 리딩과 백엔드 개발**을 맡았습니다. 백엔드 2인 중 저는 **습관·기록·리포트 도메인과 배포·문서화**를, 다른 한 명은 인증·유저 도메인을 담당했습니다.

## 맡은 범위

| 영역 | 한 일 |
| --- | --- |
| 도메인 | 습관 형성·기록·상태 갱신, 메인 화면 데이터 조회 |
| AI 연동 | Gemini 채팅 분석, FastAPI AI 서버 통신(RestTemplate) |
| 리포트 | 리포트 생성·조회, 꾸준함 지수 |
| 인프라 | Dockerfile 작성, GitHub Actions CI/CD, AWS 배포 |
| 문서 | Swagger 설정과 API 문서화 |

## AI 분석을 두 경로로 나눈 구조

습관 등록 시점에는 **Gemini API로 사용자의 채팅을 분석**해 습관을 구조화합니다. 이후 누적된 기록을 바탕으로 리포트를 만들 때는 팀의 **FastAPI AI 서버와 통신**합니다.

즉시 응답이 필요한 등록 흐름과, 누적 데이터를 다뤄야 하는 리포트 흐름의 요구가 달라 연동 대상을 나눴습니다.

## 리포트를 "실패를 읽는" 형태로 다시 짜기

초기 리포트는 결과 요약만 보여줬습니다. 서비스 컨셉이 *실패를 성공으로 만드는 것*인데 정작 리포트가 실패를 다루지 않고 있었습니다.

구성을 바꿔 **실패 이유를 아이콘으로 분류**하고, 요약을 분리하고, **꾸준함 지수**를 넣었습니다. "며칠 했다"가 아니라 "어디서 무너졌고 그래도 얼마나 이어왔다"가 읽히도록 했습니다.

## 협업에서 정한 것

- **이슈 → PR 연결을 강제.** 모든 PR이 이슈 번호를 참조하고, 작업 내용 요약과 상세를 같은 템플릿으로 적습니다.
- **API 문서를 코드와 같이 관리.** Swagger를 붙이고 `LocalTime` 스키마와 시간 JSON 포맷을 직접 설정해, 프런트가 문서만 보고 붙을 수 있게 했습니다. 응답 타입이 바뀔 때마다 문서도 같은 PR에서 갱신했습니다.
- **배포를 초반에 뚫어놨습니다.** 기능이 쌓이기 전에 Docker와 GitHub Actions를 먼저 붙여, 이후 작업이 항상 배포된 상태에서 검증되게 했습니다.
