# 3-2. 설계: 주요 결정

되돌리기 비싼 결정과 그 근거를 남긴다. 결정보다 **뒤집히는 조건**이 오래 쓸모 있으므로 항목마다 재검토 조건을 함께 적는다.

```text
§3-2-1   과거 실패 이력      결정의 전제
§3-2-2   티스토리 유지        348편을 옮기지 않는 이유
§3-2-3   Astro 직접 작성      템플릿을 쓰지 않는 이유
§3-2-4   웹폰트 미사용        추천을 따르지 않은 지점
§3-2-5   제약 목록            의도적으로 만들지 않은 것
§3-2-6   시각 언어의 출처      무엇을 보고 만들었나
§3-2-7   콘텐츠 정책          무엇을 싣고 무엇을 뺐나
§3-2-8   미결                아직 정하지 않은 것
```

## 3-2-1 과거 실패 이력

이 사이트는 세 번째 시도다. 앞선 두 번은 서로 다른 이유로 끝났고, 그 차이가 이번 설계의 근거다.

| 시도 | 끝난 이유 | 이번에 대응한 방식 |
| --- | --- | --- |
| Notion 연동 (morethan-log) | Notion 비공식 API가 바뀌며 사이트가 먹통 | 빌드에 외부 API를 두지 않는다 (§2-2 O4) |
| Gatsby 템플릿 | 글 쓰려면 에디터를 열어야 했고 손이 안 감 (군 복무 기간과 겹침) | 작성·커밋·푸시를 에이전트가 수행한다 (§2-2 O1) |
| 티스토리 | 끝나지 않음. 348편 생산 | 유지한다 (§3-2-2) |

두 번 모두 **완성된 남의 블로그를 가져다 쓴 것**이었다. 만들고 싶은 욕구는 채우지 못한 채 유지보수만 떠안는 조합이었다. 이번에는 직접 작성한다(§3-2-3).

## 3-2-2 결정: 티스토리를 유지하고 348편을 옮기지 않는다

기존 348편 중 267편이 알고리즘 풀이다. 이 글들은 검색 유입에 의존하며, 유입 대부분이 구글이다.

구글 유입은 정적 사이트로 옮겨도 SEO로 대체로 회복된다. 회복되지 않는 것은 다음·네이버 유입이다. 티스토리가 다음에서 잘 잡히는 것은 두 서비스가 같은 회사(카카오) 소속이기 때문이고, 이는 메타 태그를 다듬어 넘을 수 있는 종류가 아니다. 또한 티스토리는 외부 도메인으로 301 리다이렉트를 걸 수 없어 링크 자산을 넘길 방법도 없다.

옮겨서 손해 보는 글이 267편이므로 일괄 이관을 하지 않는다. 새 글은 이 사이트에, 기존 글은 그대로 둔다.

**재검토 조건** — 기술 회고 글이 풀이 글보다 많아지고 유입이 검색이 아니라 레퍼럴 위주가 될 때. 그때는 마크다운이 이미 있으므로 이관 비용이 낮다.

## 3-2-3 결정: 템플릿을 쓰지 않고 Astro로 직접 작성한다

Jekyll 테마(Chirpy 등)를 포크하면 한 시간 안에 더 완성도 높은 사이트가 나온다. 그럼에도 쓰지 않는다. 이 사이트의 목표 중 하나가 직접 만들어 보는 것이고(§1-2), 포크는 그 목표를 하나도 채우지 못한 채 남의 코드에 대한 유지보수 책임만 남기기 때문이다.

동시에 **전부 직접 만들지도 않는다.** 손으로 만들 가치가 있는 것과 없는 것을 나눈다.

| 직접 만든다 | 프레임워크에 맡긴다 |
| --- | --- |
| 레이아웃, 타이포, 여백 | 마크다운 파싱 |
| 글 목록·상세 화면 | 문법 하이라이팅 |
| 소개(포트폴리오) 페이지 | 프런트매터 파싱과 타입 검증 |
| 색 토큰과 다크 모드 | 정적 라우트 생성 |

Astro를 고른 이유는 이 경계에 맞기 때문이다. Content Collections가 오른쪽 열을 처리하고, HTML과 CSS는 템플릿 없이 처음부터 작성한다.

**재검토 조건** — 프레임워크 자체와 싸우는 시간이 화면을 만드는 시간보다 길어질 때.

## 3-2-4 결정: 웹폰트를 불러오지 않는다

디자인 시스템 산출(ui-ux-pro-max, Swiss Modernism 2.0)은 Archivo / Space Grotesk 조합을 권장했다. 따르지 않았다.

두 폰트 모두 **한글 글리프가 없다.** 본문이 한국어인 이 사이트에서는 어차피 시스템 폰트로 폴백되므로, 외부 요청과 폰트 로딩 지연만 늘고 실제로 바뀌는 것은 라틴 문자뿐이다. §2-3의 "외부 요청 0건"과도 충돌한다.

레이아웃 원칙(단일 칼럼, 큰 타이포, 넓은 여백)은 채택했다.

색은 이후 토스 스타일로 옮기면서 바뀌었다 — 헤어라인 구분선 대신 **면색 차이**로 영역을 나누고, 그레이 스케일에 블루 하나(포인트)와 그린 하나(운영 상태 전용)를 쓴다. 현재 토큰은 [3-1](3-1-DESIGN-ARCHITECTURE.md) §3-1-4에 있고, 시각 언어의 출처는 §3-2-6에 있다.

**재검토 조건** — 한글 웹폰트(Pretendard 등)를 자체 호스팅해 서브셋으로 넣을 때. 이 경우 외부 요청은 여전히 0건이다.

## 3-2-6 시각 언어의 출처

디자인을 백지에서 만들지 않았다. 참고한 것과 **무엇을 가져오고 무엇을 버렸는지**를 남긴다. 나중에 화면을 고칠 때 원래 무엇을 노리고 있었는지가 근거가 된다.

| 출처 | 가져온 것 | 버린 것 |
| --- | --- | --- |
| [scatterlab.co.kr](https://www.scatterlab.co.kr/) | 큰 볼드 헤드라인, 넓은 여백 | 브랜드 옐로 — 남의 브랜드 색이다 |
| `toss-tech-design` 스킬 | 라운드 카드 그룹, 카드 위 작은 라벨, **안쪽으로 들여간 구분선**, 면색으로 영역 구분, 단일 블루 포인트 | 스킬 본문 전체 |

개인 포트폴리오 사이트도 몇 곳 참고했으나 **어디를 봤는지는 남기지 않는다.** 남의 개인 사이트나 이력서를 이 저장소의 공개 문서에 목록으로 박아둘 이유가 없다. 대신 거기서 정해 실제로 구현한 것을 적는다. 아래 셋은 이제 이 사이트의 규칙이다.

### 연락 수단은 이름 바로 아래 둔다

페이지 끝까지 스크롤해야 나오면 안 된다. 히어로의 이름과 한 줄 소개 다음이 연락처 버튼 줄이다.

버튼에는 서비스명과 **실제 주소를 함께** 넣는다 — `GitHub @kangkyunghyun`처럼. 클릭하지 않아도 어디로 가는지 읽힌다. 구현은 `src/pages/index.astro`의 `links` 배열이며 `label`(굵게)과 `handle`(흐리게) 두 필드를 쓴다.

### 푸터는 3열이다

이름·직함 / Connect(외부 링크) / Quick Links(메인 섹션 앵커), 마지막 줄에 저작권. 40rem 이하에서 2열로 접히고 소개 칸이 전체 폭을 차지한다.

Quick Links는 `/#projects` 형태의 절대 경로를 쓴다. 블로그나 글 상세에서 눌러도 메인으로 이동해야 하기 때문이다. 앵커 대상 섹션에는 `scroll-margin-top`을 줘 sticky 헤더가 제목을 가리지 않게 한다.

### 프로젝트 상세는 판단 근거 순으로 쓴다

배경·해결 과정 → AS-IS → TO-BE → 구현 내용 → 결과. 읽는 사람이 "무엇이 막혔고, 무엇을 바꿨고, 얼마나 나아졌나"를 이 순서로 확인한다.

AS-IS·TO-BE만 본문이 아니라 프런트매터 배열이다. 마크다운 표로 쓰면 좁은 화면에서 깨지기 때문에 2열 카드로 그린다. 결과는 수치로 쓴다(§[4-4](4-CONTENT-OPERATIONS.md)).

### 토스 스킬은 시각 스타일 키트가 아니다

`toss-tech-design` 스킬 본문은 리서치 운영·UX 라이팅·접근성 같은 **설계 운영 방법론**이고, SKILL.md가 "토스의 시각 스타일만 흉내 내고 싶을 때는 쓰지 말 것"이라고 명시한다. 색·타이포·radius 스펙은 한 줄도 없다.

시각 근거로 쓴 것은 저장소에 함께 든 **스크린샷 2장**뿐이다. 그레이 스케일 값은 거기서 추출한 것이라 토스 실제 토큰과 미세하게 다를 수 있다. `MUST` — 이 사실을 지우지 말 것. 색을 조정할 때 "토스가 이렇다"가 아니라 "스크린샷에서 뽑았다"가 근거다.

### 결정: 아이콘은 Lucide를 유지한다

[Reicon](https://reicon.dev/icons)을 검토했다. 2,628개, MIT, 활발히 유지된다. `data/icon-data.json`에서 SVG를 뽑을 수 있어 npm 없이도 현재 방식(경로만 복사)을 유지할 수 있다.

쓰지 않기로 했다. **브랜드 아이콘이 하나도 없기 때문이다** — github·linkedin·threads 모두 0건. 범용 아이콘 라이브러리가 상표 문제로 브랜드를 빼는 것은 흔한 일이다.

이 사이트에서 아이콘이 가장 많이 노출되는 자리가 히어로 버튼과 푸터 Connect이고 그 대부분이 브랜드다. Reicon으로 바꾸면 UI 아이콘만 교체되고 브랜드는 Lucide로 남는데, **Reicon은 fill 기반이고 Lucide는 stroke 기반**이라 한 줄에 두 스타일이 섞인다. 깔끔하게 만들려는 변경이 반대 결과를 낳는다.

**재검토 조건** — 브랜드 아이콘을 Simple Icons(fill 기반)로 따로 조달할 때. 그때는 두 소스가 모두 fill이라 스타일이 맞는다.

## 3-2-8 미결

확정하지 않은 항목이다. 기준선에 확정처럼 적지 않는다.

1. **이전 블로그 종료 여부** — 이 사이트가 6개월 이상 유지되고 글이 10편 이상 쌓이기 전에는 판단하지 않는다. 과거 두 번의 실패를 고려한 유예다.
2. **초기 이관 대상** — 회고 성격 글(Diary 15, Development 7, Book 4, Security 5) 중 일부를 옮기는 안이 있으나 대상과 시점은 미정이다. 일괄 이관은 하지 않는다(§3-2-2).

4. **커스텀 도메인** — 보류(2026-08-02). 헤더 워드마크를 도메인 문자열로 쓰는 방식을 검토했으나, `*.github.io`는 소유 도메인이 아니라 호스팅 정보여서 워드마크로 쓰지 않기로 했다. 사용자 이메일이 `kyunghyun.dev@gmail.com`이라 `kyunghyun.dev`가 자연스러운 후보다. 도입한다면 GitHub Pages는 커스텀 도메인을 무료로 지원하므로 `CNAME` 파일과 DNS, `astro.config.mjs`의 `site` 값만 바꾸면 된다. **검색 인덱스가 적을수록 이전 비용이 싸므로 미루면 비용이 커진다.**
