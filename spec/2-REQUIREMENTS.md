# 2. 요구사항

독자와 운영자를 한 문서에 합쳤다. 운영자가 한 명이고 독자 동선이 짧아 문서를 나눌 실익이 없다.

```text
§2-1   독자 사용 사례     방문자가 하려는 일
§2-2   운영자 요구사항     글을 쓰고 내보내는 쪽의 요구
§2-3   품질 기준          측정 가능한 선
```

## 2-1 독자 사용 사례

**U1. 글을 찾아 읽는다.** 목록에서 제목과 날짜를 보고 고른다. 목록은 최신순이며 초안(`draft: true`)은 나오지 않는다. `MUST`

**U2. 필자가 누구인지 확인한다.** 소개 페이지에서 소속, 진행 중인 활동, 만든 것, 자격, 외부 링크를 한 화면 흐름으로 읽는다. 채용·협업 판단에 필요한 정보가 여기서 끝나야 한다. `MUST`

**U3. 코드가 포함된 글을 모바일에서 읽는다.** 코드 블록은 블록 안에서만 가로 스크롤되고 페이지 전체가 밀리면 안 된다. `MUST`

**U4. 이전 블로그로 넘어간다.** 알고리즘 풀이를 찾는 독자는 이전 블로그로 유도돼야 한다. 소개 페이지와 푸터에 링크를 둔다. `SHOULD`

## 2-2 운영자 요구사항

**O1. 에디터를 열지 않고 글을 낸다.** 작성부터 커밋·푸시까지 에이전트가 수행한다. 운영자가 직접 IDE를 여는 순간이 없어야 한다. 과거 Gatsby 템플릿을 놓은 직접적 원인이 이것이다. `MUST`

**O2. 발행이 별도 행위가 아니다.** `main`에 푸시하면 배포된다. 푸시와 분리된 "배포 버튼"이 존재하면 안 된다. Notion 연동 시절의 실패 원인이 이것이다. `MUST`

**O3. 글이 이식 가능한 형식으로 남는다.** 글은 표준 마크다운 파일이며 프런트매터 외의 독자 문법을 쓰지 않는다. 이 사이트가 사라져도 글은 다른 곳에서 그대로 렌더링돼야 한다. `MUST`

**O4. 외부 서비스가 사이트 수명을 결정하지 않는다.** 빌드에 외부 API 호출이 없어야 한다. Notion 비공식 API가 바뀌며 이전 블로그가 죽은 전례가 있다. `MUST`

**O5. 레이아웃을 고치지 않고도 글을 쓸 수 있다.** 글쓰기와 사이트 수정이 서로를 막지 않아야 한다. `SHOULD`
